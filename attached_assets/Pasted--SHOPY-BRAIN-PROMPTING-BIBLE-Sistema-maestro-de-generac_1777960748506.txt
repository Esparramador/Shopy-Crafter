# SHOPY BRAIN · PROMPTING BIBLE

**Sistema maestro de generación de prompts para informes profesionales**

Versión: 1.0 · Mayo 2026
Modelos primarios: Claude Opus 4.7 · Gemini 2.5 Pro (fallback)

---

## ⚡ PROPÓSITO

Este documento es la **constitución de Shopy Brain**. Define cómo estructurar
TODO prompt que vaya a Claude/Gemini para generar informes, contenido,
análisis o cualquier output que vaya a manos del usuario final.

**REGLA DE ORO:**
> Si el output no se entiende en 30 segundos por alguien que no conoce
> el contexto, el prompt está mal estructurado. La inteligencia está
> en hacer lo complejo simple, no al revés.

---

## 📐 ARQUITECTURA UNIVERSAL DEL PROMPT

Todo prompt de Shopy Brain debe seguir esta estructura de 7 bloques en este orden:

```
1. ROLE          → Quién es la IA (rol profesional específico)
2. CONTEXT       → Qué empresa/producto/situación
3. DATA          → Datos reales en formato estructurado
4. TASK          → Qué exactamente debe hacer
5. CONSTRAINTS   → Reglas duras inviolables
6. OUTPUT_FORMAT → Estructura JSON/Markdown exacta esperada
7. EXAMPLES      → 1-2 ejemplos de output deseado (few-shot)
```

**Sin esta estructura, los outputs son inconsistentes, alucinan datos, o
producen formatos incompatibles con los Builders de documentos.**

## 🎭 BLOQUE 1 — ROLE (rol profesional)

### Regla
NO uses "Eres una IA" ni "Eres un asistente". Asigna un **rol profesional
humano específico** con años de experiencia y especialidad.

### Plantilla
```
Eres {ROL_ESPECÍFICO} con {AÑOS} años de experiencia en {SECTOR}.
Has trabajado con {TIPO_CLIENTES} y eres especialista en {ESPECIALIDAD}.
Tu estilo es {TONO}: {ADJETIVO_1}, {ADJETIVO_2}, sin {ANTI_PATRÓN}.
```

### Roles por tipo de informe

| Tipo de informe | Rol asignado |
|-----------------|--------------|
| COGS hostelería | Consultor financiero F&B con 20 años, MBA por IESE, ha optimizado costes en 200+ hoteles |
| Comparativa proveedores | Director de compras con 15 años en grandes cuentas hostelería y retail |
| Pricing estratégico | Pricing Manager con experiencia en e-commerce (Amazon, Shopify Plus) y consumo |
| Análisis competencia | Analista de inteligencia competitiva con background en consultoría estratégica (BCG/McKinsey style) |
| A/B testing reporte | Growth analyst senior con dominio estadístico (intervalos confianza, significancia) |
| Auditoría tienda | Auditor e-commerce certificado, especialidad en Shopify Plus y conversion optimization |
| Contrato proveedor | Abogado mercantil español, 10 años en derecho de contratos B2B y compliance RGPD |
| Resumen ejecutivo | Consultor estratégico (estilo McKinsey) — claro, accionable, sin jerga |
| Landing page producto | Copywriter direct-response con experiencia en e-commerce (Amazon, Shopify) |
| Reporte trimestral | CFO de scaleup con foco en métricas SaaS/e-commerce |
| Informe SEO | SEO senior con expertise en Shopify, Search Console y semantic SEO |
| Análisis imagen producto | Director de arte con 15 años en e-commerce visual y product photography |

### Ejemplo bien construido
```
Eres consultor financiero senior especializado en F&B con 20 años de
experiencia. Has optimizado estructuras de costes en más de 200 hoteles
y restaurantes en España. Tu estilo es ejecutivo: directo al grano,
basado en datos, sin jerga financiera innecesaria. NO usas eufemismos
ni palabras de relleno tipo "potencialmente" o "podría considerarse".
```

### Ejemplo mal construido (no hacer)
```
Eres una IA útil que ayuda con análisis financieros. Por favor, sé
profesional y servicial.
```

## 🏢 BLOQUE 2 — CONTEXT (contexto de negocio)

### Regla
Inyecta TODO el contexto relevante antes de pedir nada. La IA no puede
inferir lo que no le dices, y cuando "infiere" → alucina.

### Plantilla
```
EMPRESA: {nombre_empresa}
SECTOR: {sector_específico}
TAMAÑO: {empleados o facturación}
PAÍS / IDIOMA: {país} / {idioma_documento}
MONEDA: {EUR / USD / etc}
PRODUCTO/SERVICIO ANALIZADO: {nombre_producto}
CATEGORÍA: {categoría_específica}
PERIODO ANÁLISIS: {fechas exactas}
DESTINATARIO DEL INFORME: {quién lo va a leer}
OBJETIVO DEL INFORME: {decisión que se debe tomar tras leerlo}
```

### Por qué importa el destinatario
El nivel técnico del lector cambia COMPLETAMENTE el output:

| Destinatario | Nivel técnico | Estilo |
|--------------|---------------|--------|
| CEO / Inversor | Alto en negocio, bajo en operativa | Foco en KPIs, ROI, riesgos. Sin detalle operativo. |
| Equipo financiero | Alto en finanzas | Detalle de fórmulas, supuestos, sensibilidad |
| Operaciones | Alto en operativa | Detalle de procesos, plazos, responsables |
| Marketing | Alto en growth | Foco en métricas conversión, CAC, LTV |
| Legal / Compliance | Alto en legal | Cláusulas, riesgos legales, RGPD |
| Cliente externo | Variable | Lenguaje accesible, sin jerga interna |

### Ejemplo
```
EMPRESA: Hotel Mediterráneo (boutique 4*, 38 habitaciones)
SECTOR: Hostelería · F&B premium
PAÍS / IDIOMA: España / Español
MONEDA: EUR
PRODUCTO ANALIZADO: Carta de vinos (categoría tintos Rioja Crianza)
PERIODO: Q1 2026 (enero-marzo)
DESTINATARIO: Director financiero del hotel
OBJETIVO: Decidir si cambiar de proveedor actual a uno nuevo, con
          ahorro estimado y plan de transición a 90 días.
```

## 📊 BLOQUE 3 — DATA (datos estructurados)

### Regla
NUNCA mezcles datos con instrucciones. Los datos van en bloque separado,
SIEMPRE en formato estructurado (JSON o tabla markdown).

### Anti-patrón (no hacer)
```
"El precio actual es de 10,99€ y vendemos unas 100 unidades al mes,
con un margen de aprox 60% según mis estimaciones..."
```

### Patrón correcto
```
DATOS:
{
  "currentPrice": 10.99,
  "currency": "EUR",
  "monthlyVolume": { "low": 80, "avg": 100, "high": 130 },
  "currentMargin": 0.60,
  "marginConfidence": "estimated"
}
```

### Reglas para los datos

1. **Tipa todo**: number vs string vs boolean. La IA respeta los tipos
   si los ve estructurados.

2. **Marca incertidumbre**: si un dato es estimado vs medido vs
   confirmado, dilo:
   ```json
   { "value": 1500, "source": "estimated", "confidence": 0.6 }
   ```

3. **Rangos en lugar de números fijos** cuando sea variable:
   ```json
   { "low": 5.20, "avg": 7.40, "high": 9.80, "currency": "EUR" }
   ```

4. **Unidades explícitas**: nunca `"price": 4.20`, siempre
   `"price": 4.20, "currency": "EUR", "unit": "per_bottle"`.

5. **Fechas en ISO 8601**: `"2026-03-15"`, no `"15/3/26"`.

6. **Si falta un dato**: pásalo como `null` con razón:
   ```json
   { "marketShare": null, "reason": "data_not_available" }
   ```

## 🎯 BLOQUE 4 — TASK (instrucción específica)

### Regla
Una sola tarea por prompt. Si necesitas 3 cosas distintas, son 3 prompts.
Pedir 3 cosas en uno → la IA hace mal las 3.

### Plantilla
```
TAREA:
Genera {ARTEFACTO} que sirva para {OBJETIVO_NEGOCIO}.

Debe incluir:
1. {ELEMENTO_1}
2. {ELEMENTO_2}
3. {ELEMENTO_3}

Foco en: {QUÉ_PRIORIZAR}
Profundidad: {SUPERFICIAL / MEDIA / EXHAUSTIVA}
```

### Verbos de tarea por intención

| Intención | Verbo en prompt |
|-----------|-----------------|
| Análisis | "Analiza", "Evalúa", "Diagnostica" |
| Recomendación | "Recomienda", "Sugiere", "Prioriza" |
| Comparación | "Compara", "Contrasta", "Benchmarkea" |
| Generación | "Genera", "Redacta", "Construye" |
| Predicción | "Proyecta", "Estima", "Pronostica" |
| Síntesis | "Resume", "Sintetiza", "Extrae conclusiones" |

### Ejemplo
```
TAREA:
Genera un análisis comparativo de COGS entre los 3 proveedores listados,
que sirva para decidir cuál contratar para los próximos 12 meses.

Debe incluir:
1. Cálculo TCO (Total Cost of Ownership) por proveedor incluyendo
   costes ocultos (transporte, rotura, almacenamiento)
2. Ranking según volumen anual estimado (2.400 botellas)
3. Recomendación clara con justificación cuantitativa
4. Plan de transición de 90 días si se cambia de proveedor

Foco en: ahorro económico y reducción de riesgo de stock-out
Profundidad: EXHAUSTIVA — el director financiero usará esto para decidir
```

## 🚧 BLOQUE 5 — CONSTRAINTS (reglas duras inviolables)

### Regla
Las restricciones evitan alucinación. Sé EXPLÍCITO con lo que NO debe hacer.

### Constraints universales (incluir SIEMPRE)

```
RESTRICCIONES INVIOLABLES:

1. PRECISIÓN DE DATOS
   - Si un dato no está en DATA, NO lo inventes. Marca como null o
     escribe "Dato no disponible".
   - NO uses estadísticas genéricas tipo "según estudios" sin fuente.
   - Si haces una asunción, decláralay justifica.

2. CIFRAS Y CÁLCULOS
   - Todos los cálculos deben ser explicables paso a paso.
   - Usa máximo 2 decimales para dinero, 1 para porcentajes.
   - NUNCA inventes precios, márgenes o métricas que no estén en DATA.

3. TONO Y ESTILO
   - Sin jerga corporativa hueca ("sinergia", "leverage",
     "potencialmente disruptivo")
   - Sin condicionales de relleno ("podría", "tal vez", "es posible que")
     cuando los datos permiten ser concluyente.
   - Frases cortas. Una idea por frase.

4. COMPLETITUD
   - Si la respuesta requiere asunciones, lístalas al inicio.
   - Si hay riesgos importantes, decláralos explícitamente.
   - No omitas información negativa para hacer el informe "más positivo".

5. FORMATO
   - Respeta EXACTAMENTE el OUTPUT_FORMAT especificado.
   - No añadas markdown si te piden JSON puro.
   - No envuelvas el JSON en bloques ```json a menos que se pida.
```

### Constraints específicas según tipo de informe

**Para informes financieros:**
```
- Todos los importes en {moneda} con símbolo
- Sigue principios contables españoles (PGC) si aplica
- Si calculas IVA, usa tipo del país (España: 21% general, 10% reducido)
- Distingue claramente: bruto vs neto, antes/después de impuestos
```

**Para informes legales (contratos):**
```
- Lenguaje formal jurídico español
- Referencias a normativa vigente española y UE
- RGPD (Reglamento UE 2016/679) y LOPDGDD (Ley 3/2018)
- Cláusulas numeradas en formato 1., 1.1., 1.1.1.
- Fórmulas estándar: "Las partes acuerdan...", "El presente contrato..."
```

**Para informes de marketing/copy:**
```
- Lenguaje accesible, sin tecnicismos
- Frases activas (no pasivas)
- Beneficios > características
- Llamada a acción clara y única por sección
- Adaptado al buyer persona específico
```

## 🎨 BLOQUE 7 — EXAMPLES (few-shot learning)

### Regla
Para informes complejos o nuevos, incluye 1-2 ejemplos de output deseado.
Esto reduce alucinaciones un 60-80% y garantiza consistencia.

### Plantilla
```
EJEMPLO DE OUTPUT DESEADO:

Para un caso similar (datos ficticios), el output sería:

{
  "metadata": { ... },
  "executiveSummary": {
    "headline": "Cambiar a Bodegas García ahorra €11.200/año con menor riesgo",
    "keyFindings": [
      "TCO 23% más bajo que proveedor actual",
      "Lead time 2 días vs 5 días actuales",
      "Misma o mejor calidad según 3 catas ciegas"
    ],
    "recommendation": "Iniciar transición en 90 días con piloto 30%",
    "estimatedImpact": "€11.200 ahorro anual"
  },
  ...
}

Sigue EXACTAMENTE esta estructura para el caso real.
```

## 🧠 META-INSTRUCCIONES PARA SHOPY BRAIN

Cuando Shopy Brain construye un prompt para Claude/Gemini, debe:

### 1. Auto-validar la calidad del prompt antes de enviarlo

```typescript
// Pseudo-código del proceso interno
function validatePrompt(prompt: PromptStructure): ValidationResult {
  const checks = {
    hasRole: !!prompt.role && prompt.role.length > 50,
    hasContext: !!prompt.context && Object.keys(prompt.context).length >= 5,
    hasStructuredData: typeof prompt.data === 'object',
    hasClearTask: !!prompt.task && prompt.task.includes('Genera'),
    hasConstraints: prompt.constraints.length >= 5,
    hasOutputFormat: !!prompt.outputFormat,
    dataIsTyped: validateTypes(prompt.data),
  };

  return {
    valid: Object.values(checks).every(Boolean),
    failures: Object.entries(checks).filter(([_, v]) => !v).map(([k]) => k),
  };
}
```

Si el prompt no pasa validación → enriquecerlo automáticamente con
defaults sensatos antes de enviar.

### 2. Adaptar el modelo según complejidad

| Tarea | Modelo recomendado | Razón |
|-------|-------------------|-------|
| Resumen simple, extracción datos | Gemini Flash o Claude Haiku | Rápido, barato |
| Análisis financiero, COGS, contratos | Claude Opus 4.7 | Máxima precisión numérica |
| Copy creativo, landing pages | Claude Opus 4.7 o Gemini Pro | Creatividad + control |
| Análisis imágenes producto | Claude Opus 4.7 (vision) | Vision + razonamiento |
| Cálculos masivos en batch | Gemini Pro | Throughput |
| Razonamiento estratégico complejo | Claude Opus 4.7 | Mejor reasoning |

### 3. Manejo de fallback

```
Si Claude falla (rate limit, error, timeout):
  → Reintentar 1 vez tras 2s
  → Si vuelve a fallar → Gemini con MISMO prompt
  → Si Gemini también falla → guardar error + alertar usuario

NUNCA devolver datos de placeholder al usuario sin avisar.
```

### 4. Cache de prompts repetitivos

Si el mismo `(productId, reportType, dataHash)` se ha generado en
las últimas 24h y los datos no han cambiado significativamente
(< 5% diferencia en KPIs clave) → reutilizar resultado anterior.

Esto puede ahorrar 40-60% de costes IA.

### 5. Logging exhaustivo

Cada llamada a Claude/Gemini debe registrarse en `ai_generations`:

```sql
INSERT INTO ai_generations (
  id, shop_id, user_id, report_type, model_used,
  prompt_tokens, completion_tokens, cost_eur,
  latency_ms, success, error_message,
  prompt_hash, output_summary, created_at
) VALUES (...);
```

Esto permite:
- Auditar coste por sección/producto/usuario
- Detectar prompts que fallan más
- A/B test de prompts (versionado)
- Cumplimiento RGPD (datos personales en prompts)

### 6. Versionado de prompts

Cada plantilla maestra debe tener versión:
```typescript
const PROMPT_VERSIONS = {
  'cogs-excel': 'v3.2',
  'pptx-executive': 'v2.8',
  'price-recommendation': 'v4.1',
};
```

Cuando cambies un prompt, sube la versión. Esto te permite:
- Revertir si la nueva versión empeora outputs
- Comparar performance entre versiones
- Mantener compatibilidad con informes históricos

### Estructura recomendada

```typescript
// /server/services/reports/ai/ShopyBrain.ts

import Anthropic from '@anthropic-ai/sdk';
import { GoogleGenerativeAI } from '@google/generative-ai';

interface PromptStructure {
  role: string;
  context: Record<string, unknown>;
  data: Record<string, unknown>;
  task: string;
  constraints: string[];
  outputFormat: object;
  examples?: object[];
}

class ShopyBrain {
  private claude: Anthropic;
  private gemini: GoogleGenerativeAI;
  private promptVersion = '1.0';

  async generate<T>(
    template: PromptTemplate,
    inputs: Record<string, unknown>
  ): Promise<T> {
    // 1. Construir prompt con la plantilla y los inputs
    const prompt = this.buildPrompt(template, inputs);

    // 2. Validar el prompt antes de enviarlo
    const validation = this.validatePrompt(prompt);
    if (!validation.valid) {
      throw new Error(`Invalid prompt: ${validation.failures.join(', ')}`);
    }

    // 3. Verificar caché (si existe entrada reciente con datos similares)
    const cached = await this.checkCache(template, inputs);
    if (cached) return cached as T;

    // 4. Elegir modelo según complejidad
    const model = this.selectModel(template.type);

    // 5. Llamar al modelo con retry y fallback
    const result = await this.callWithFallback<T>(model, prompt);

    // 6. Validar output (es JSON válido + cumple schema)
    this.validateOutput<T>(result, template.outputSchema);

    // 7. Loggear en ai_generations
    await this.logGeneration(template, inputs, result);

    // 8. Guardar en caché
    await this.saveToCache(template, inputs, result);

    return result;
  }

  private buildPrompt(template: PromptTemplate, inputs: Record<string, unknown>): string {
    return [
      template.role,
      '',
      'CONTEXTO:',
      this.formatContext(inputs),
      '',
      'DATOS:',
      JSON.stringify(inputs.data, null, 2),
      '',
      'TAREA:',
      template.task,
      '',
      'RESTRICCIONES INVIOLABLES:',
      template.constraints.map((c, i) => `${i + 1}. ${c}`).join('\n'),
      '',
      'OUTPUT_FORMAT:',
      'Devuelve ÚNICAMENTE un JSON válido siguiendo esta estructura exacta.',
      'NO incluyas texto antes ni después. NO uses bloques markdown.',
      '',
      JSON.stringify(template.outputFormat, null, 2),
      template.examples ? `\nEJEMPLOS:\n${JSON.stringify(template.examples, null, 2)}` : '',
    ].join('\n');
  }

  private async callWithFallback<T>(model: string, prompt: string): Promise<T> {
    try {
      return await this.callClaude<T>(prompt);
    } catch (err) {
      console.warn('Claude failed, falling back to Gemini', err);
      return await this.callGemini<T>(prompt);
    }
  }

  private async callClaude<T>(prompt: string): Promise<T> {
    const response = await this.claude.messages.create({
      model: 'claude-opus-4-7',
      max_tokens: 4000,
      messages: [{ role: 'user', content: prompt }],
    });

    const text = response.content[0].type === 'text' ? response.content[0].text : '';
    return JSON.parse(text) as T;
  }
}

export const shopyBrain = new ShopyBrain();

function evaluateOutput(output: unknown, type: ReportType): QualityScore {

## 📚 GLOSARIO DE TÉRMINOS

| Término | Significado en Shopy Brain |
|---------|---------------------------|
| **Prompt maestro** | Template completo con los 7 bloques |
| **Prompt enriquecido** | Master + datos reales inyectados |
| **Output validado** | JSON que pasó schema + checklist de calidad |
| **Builder** | Clase que convierte JSON en archivo final (xlsx, pptx, etc) |
| **Confidence score** | 0-1, qué tan seguro está el modelo del output |
| **Warning** | Aviso del modelo de algo que el usuario debe revisar |
| **Assumption** | Asunción que hizo el modelo por falta de dato |
| **Hallucination** | Dato inventado por el modelo (a evitar) |
