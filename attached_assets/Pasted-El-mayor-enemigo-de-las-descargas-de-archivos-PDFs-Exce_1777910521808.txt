El mayor enemigo de las descargas de archivos (PDFs, Excel, MP4) generadas por IA es el "Falso Positivo". A veces, la API de Runway o ElevenLabs falla, pero en lugar de devolver un archivo de vídeo/audio, devuelve un archivo de texto con un mensaje de error ({"error": "Rate limit exceeded"}). Si tu backend no revisa qué tipo de archivo ha recibido y se lo envía al usuario como un .mp4, cuando el usuario intente abrirlo en su ordenador le dirá "Archivo corrupto". ¡Eso es un fallo silencioso letal!

Para blindar absolutamente todos los rincones de tu app (texto, análisis, descargas de archivos) sin crear archivos nuevos, vamos a darle a Replit un prompt de "Inyección de Middleware de Resiliencia y Control de Integridad".

Copia y pega este Mega-Prompt para tu agente en Replit:

Misión Crítica: Erradicación de Fallos Silenciosos, Blindaje 4xx/5xx y Control de Integridad de Archivos
Actúa como Lead SRE (Site Reliability Engineer). Necesito que audites y modifiques el código EXISTENTE de todas nuestras integraciones (Claude, Gemini, Runway, ElevenLabs, Replicate) para erradicar los fallos silenciosos, los cuelgues por Timeouts y la corrupción de archivos descargables.

NO CREES ARCHIVOS NUEVOS. Aplica esta lógica directamente en las funciones y controladores actuales.

FASE 1: El Protocolo "Anti-Fallo Silencioso" (Manejo de Promesas)

Revisa TODAS las llamadas asíncronas (await fetch, await axios, etc.).

Asegúrate de que TODAS estén dentro de bloques try/catch estrictos.

Si usas fetch, inyecta la validación de respuesta: si !response.ok, lanza un error explícito capturando el status (4xx/5xx) y el cuerpo del error, en lugar de dejar que el código continúe y asuma que todo fue bien.

FASE 2: Inyección de Resiliencia (Rate Limits y Exponential Backoff)
Dentro del catch de cada llamada a API existente, implementa este flujo:

Errores 429 (Rate Limit): Extrae la cabecera Retry-After. Haz que la función ejecute un await sleep(segundos) y vuelva a intentar la llamada.

Errores 5xx / Timeouts: Implementa un bucle de reintento con retroceso exponencial (ej. 1s, 2s, 4s) hasta un máximo de 3 intentos.

FASE 3: Control de Integridad de Entregables (¡CRÍTICO!)
Para las funciones que generan archivos (Excels, PDFs, MP4 de Runway, MP3 de ElevenLabs):

Antes de guardar el archivo temporal en el servidor o enviarlo al frontend, DEBES comprobar el Content-Type de la respuesta de la API.

Si esperábamos un vídeo (video/mp4) o un Excel y la API devuelve un application/json, el sistema debe detectar que es un error de la API, bloquear la descarga corrupta, y activar la lógica de reintento de la Fase 2.

FASE 4: Degradación Elegante (Comunicación al Frontend)
Si después de todos los reintentos la API externa sigue caída, el backend NUNCA debe devolver un error HTML crudo o dejar la petición colgada.
Debe devolver SIEMPRE un JSON estandarizado al frontend: { "success": false, "error_code": "API_TIMEOUT", "message": "El motor de generación está saturado. Por favor, intenta de nuevo en unos minutos.", "is_retryable": true }.

Tu Tarea: Localiza un controlador existente que genere un archivo (por ejemplo, el que genera el vídeo o el reporte financiero en Excel). Muéstrame el código de cómo vas a inyectar el bloque try/catch, la validación del Content-Type para evitar archivos corruptos, y el sistema de reintentos. Espero tu respuesta con el código modificado antes de aplicar los cambios al resto de archivos.

Por qué esto hace que tu plataforma sea "Indestructible"
Fin de los "Archivos Corruptos": Al revisar el Content-Type (Fase 3), tu sistema se vuelve inteligente. Sabe diferenciar si ElevenLabs le ha devuelto un audio real o un mensaje de error disfrazado, protegiendo al usuario final.

Fin de los Cuelgues Infinitos: Al controlar los Timeouts y capturar los errores, garantizas que la interfaz de usuario de Shopy Crafter siempre reciba una respuesta (ya sea el éxito o un aviso limpio), lo que permite que el botón de carga vuelva a la normalidad en lugar de girar eternamente.
